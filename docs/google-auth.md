# Google identity API (in progress)

This backend implements the server-side Google OpenID Connect authorization-code flow described in [Google's documentation](https://developers.google.com/identity/openid-connect/openid-connect), with state, nonce and PKCE, MySQL-backed one-use flows and server-side sessions. The frontend remains a local-only preview; an opt-in authentication mode integrates these endpoints. Mock identity-provider tests are not proof of a live Google login.

The service uses `COKE_GROK_PUBLIC_ORIGIN` (an HTTPS base URL, or HTTP loopback for development; an optional slash-delimited path prefix is supported), `COKE_GROK_GOOGLE_CLIENT_ID`, `COKE_GROK_GOOGLE_SECRET_FILE`, `COKE_GROK_MYSQL_HOST`, `COKE_GROK_MYSQL_PORT` (default 3306), `COKE_GROK_MYSQL_USER`, `COKE_GROK_MYSQL_PASSWORD_FILE`, and `COKE_GROK_MYSQL_DATABASE`. Secret files must be private (no group/other permissions). It binds to `127.0.0.1:3001` by default; `COKE_GROK_AUTH_HOST` and `COKE_GROK_AUTH_PORT` override this. Run `npm run start:auth`. The database must already exist; startup creates the identity tables. The Google OAuth client must register the exact callback `<base URL>/auth/google/callback`.

A trusted reverse proxy must preserve the public Host, terminate HTTPS, and route `/api/auth/` and `/auth/google/callback` to this service. Do not log callback query strings or cookies. Do not expose this service publicly until its deployment, secrets, origin, and browser flow have been verified. An independently bundled frontend and auth runtime have been smoke-tested in an isolated K3D deployment; a public release remains future work.

For isolated tests, start a disposable MySQL instance with an empty root password accessible only on loopback, then set `COKE_GROK_TEST_MYSQL_PORT` and run `npm run test:auth` and `npm run test:mysql`. Tests create and drop their own randomly named databases. Never point them at an existing shared database server.

## Browser integration

Set `VITE_REQUIRE_AUTH=true` when starting or building the frontend to enable the login gate; without it the app is an unauthenticated visual-research preview. For local Vite development, set `VITE_AUTH_PROXY_TARGET` to the local auth service URL. Configure `COKE_GROK_PUBLIC_ORIGIN` to the browser-facing Vite URL, not the backend port. For a prefix such as `/grok-bot/`, set `VITE_BASE_PATH=/grok-bot/` and `COKE_GROK_PUBLIC_ORIGIN` to the origin plus `/grok-bot`; the proxy must preserve the prefix, and Google must register the prefixed callback. A production reverse proxy must route both the frontend and auth paths under the same origin and preserve any prefix. `VITE_REQUIRE_AUTH` is embedded at build time and is not an authorization boundary by itself. The API must enforce authorization independently.

Preview data is scoped by tenant and user IDs in browser localStorage to avoid accidental display when switching accounts. It is not secure storage, server-persisted data, or a substitute for backend authorization: other scripts or users with access to the browser profile can inspect it. Actual Bot data must be stored and authorized on the server.

`npm run test:auth-browser` uses a local simulated identity provider but real Chromium, the frontend proxy, the HTTP auth service and disposable MySQL. It checks login, refresh, sign-out and account switching in one browser profile. It does not contact Google and is not live OAuth acceptance.

To test prefix routing, run `COKE_GROK_TEST_BASE=/grok-bot/ npm run test:auth-browser` with the disposable MySQL test port set. The browser test checks the callback, cookie path, session recovery and account switching through the prefixed route.

## Google OAuth network access

`COKE_GROK_GOOGLE_OAUTH_PROXY_URL` optionally sets a dedicated HTTP(S) proxy origin for the Google client transporter. It must not contain credentials, a path, query, or fragment. This setting applies to Google token exchange and certificate retrieval; it does not modify the machine's global proxy. One-use authorization-code exchanges have retries disabled. `npm run test:google-proxy` checks proxy configuration and proves a failed proxied exchange is attempted only once with a local simulated proxy.

On 2026-10-28, direct access from this Mac to Google's OpenID configuration timed out, while the existing loopback HTTP proxy returned HTTP 200. A loopback address inside a K3D Pod refers to the Pod itself, not the Mac; use an explicitly tested host-accessible endpoint for Pod deployments. No live Google sign-in has yet been verified.

## Auth runtime image

Build with `VITE_REQUIRE_AUTH=true VITE_BASE_PATH=/grok-bot/ npm run build:deployment`, choosing the actual slash-terminated public prefix, followed by `docker build -f Dockerfile.auth -t coke-grok-auth:<version> .`. The image runs as the non-root `node` user and serves the authenticated frontend and auth API from the same origin. Startup checks that the build requires authentication and its prefix matches `COKE_GROK_PUBLIC_ORIGIN`. Secret files must be readable by that UID and have no group or other permissions. For K3D, provision appropriately owned private files rather than assuming default projected Secret permissions satisfy this requirement. Do not put secret values in the build context, image, or Docker environment.

The bundle and local ARM64 image were tested against a disposable MySQL instance using a synthetic OAuth client. `COKE_GROK_TEST_IMAGE=coke-grok-auth:local-test npm run test:bundle` runs the image test with a disposable test MySQL port set; the ordinary `npm run test:bundle` tests the host bundle. These checks do not prove real OAuth, browser login, K3D deployment, persistent storage, public access, or release rollback.

## K3D smoke test

`deploy/k3d/auth.yaml` is a local-test manifest, not a release. It expects a namespace containing `auth-config` (the non-secret `COKE_GROK_PUBLIC_ORIGIN`, `COKE_GROK_GOOGLE_CLIENT_ID`, `COKE_GROK_MYSQL_HOST`, `COKE_GROK_MYSQL_PORT`, `COKE_GROK_MYSQL_USER` and `COKE_GROK_MYSQL_DATABASE`) and `auth-secrets` (keys `mysql-password` and `google-secret`). It uses the imported local image `coke-grok-auth:local-test`; production must instead use an immutable image and independently provisioned credentials. The init container copies Secret files into a memory-backed volume and assigns ownership to UID 1000; the main container runs as UID 1000 with a read-only root filesystem. Readiness checks the service and a bounded MySQL query; it does not verify Google login or proxy egress.

On 2026-10-28, an isolated K3D namespace `coke-grok-auth-test-153c190616c2` was used with a disposable MySQL container on the local K3D Docker network and synthetic Google credentials. The deployed Pod started, read the private files, migrated the separate test database and returned the expected unauthenticated response and prefixed Google authorization redirect through a local port-forward. The test Deployment was scaled to zero afterward; its namespace and synthetic configuration remain. The disposable test database and account were removed with the test container. No existing project database was modified.

`npm run test:k3d-auth` requires `COKE_GROK_TEST_MYSQL_PORT` and `COKE_GROK_TEST_MYSQL_K3D_HOST` for a disposable test MySQL container and checks the expected K3D context. It creates a uniquely named namespace and leaves its Deployment scaled to zero. This is not a real Google login, proxy egress test, public deployment, persistent database, or release acceptance. The Mac proxy listens on `127.0.0.1`; Pod loopback is separate. A Pod may be able to reach the Mac proxy through a Docker Desktop host alias, as tested below.

On 2026-10-28, a second isolated K3D test (`coke-grok-auth-test-a28127d633e0`) additionally opened the bundled login page in headless Chrome through the service port-forward. Its test Deployment was scaled to zero. The test used synthetic Google credentials; it did not sign in to Google.

## Pod-to-Google egress evidence

On 2026-10-28, temporary Pods in `coke-grok-auth-test-a28127d633e0` reached the Google OpenID discovery endpoint over HTTPS with HTTP 200 through `http://host.docker.internal:7890` and `http://host.k3d.internal:17891`. The project's bundled `google-auth-library` also fetched Google signing certificates through `http://host.docker.internal:7890`; `scripts/google-egress-probe.ts` emits only success and the certificate count. The Pods have completed and remain in the namespace. These results apply to the current Docker Desktop/K3D network and running host proxy; they do not prove that a real OAuth authorization-code exchange or Google browser login works. Re-test after network changes. Do not assume the host aliases or ports exist on other machines.

## K3D ingress preparation

`deploy/k3d/auth-ingress.yaml` provides a Traefik `/grok-bot` prefix route to the auth service in its own namespace. It preserves the path rather than stripping it. The client build must use `VITE_REQUIRE_AUTH=true VITE_BASE_PATH=/grok-bot/`, and the runtime public origin must end in `/grok-bot`. As of 2026-10-29, a read-only inspection found existing ingress paths `/router`, `/app`, `/dingtalk-oauth`, and `/auth`; this does not prove future absence of conflicts. The manifest passed `kubectl create --dry-run=client` only; it has not been applied or tested through Traefik, the VPS, or Google. Verify all ingress routes and choose the public host and callback before deploying. The VPS must terminate TLS and forward to the Mac only, with no credentials or callback query strings logged.

On 2026-10-29, the ingress manifest was applied temporarily in `coke-grok-ingress-check-20261029` against a synthetic HTTP echo Deployment. Through the K3D Traefik listener on port 18080, `/grok-bot/api/auth/me` reached the echo service with the full path intact. The first attempt fell through to an existing root route because the synthetic Service lacked the manifest's named `http` port; after naming the test port and allowing Traefik to reconcile, the request returned the expected echo. The temporary ingress was removed and the test Deployment scaled to zero; the namespace and workload specification remain. This validates local routing only, not the auth application, TLS, Google or VPS flow.
