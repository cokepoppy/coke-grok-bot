# Pi runtime integration, in progress

The model is configured instance-wide. Bot data, sessions, workspaces and runs remain scoped to a user and tenant. Do not put a provider key in the tenant workspace, an image, a source file, Git, task events or logs. The model gateway accepts only short-lived, call-limited run capabilities and replaces the capability with the provider credential in its own process. The gateway is an internal service and must never be attached to the public ingress. A capability is still a bearer credential during its short lifetime and must not be recorded in task data or logs.

The gateway limits request size and output tokens, fixes the configured model and upstream route, disallows redirects, suppresses provider error bodies, aborts on revocation or timeout, and redacts the raw provider credential even across streaming chunk boundaries. It does not by itself implement per-user network isolation or prove that an arbitrary process cannot steal a capability. Those boundaries are part of the pending computer and run integration.

`agent_runs` and `agent_run_events` are an additive MySQL queue schema. A request ID deduplicates creation per Bot. Claims lock the user's membership and permit at most one running or unresolved run across that user's Bots. Expired leases become `unknown`; they are not automatically retried, and they block later runs for that user until a future reconciliation mechanism resolves the uncertainty. The store is not yet wired into the production HTTP service or scheduler.

## Integration work

The current feature branch adds a persistent scheduler, a Pi dispatcher, an optional authenticated run API, and a desktop provisioner. None is enabled in the public service yet. A scheduler claims at most one run per user's computer, renews leases, and keeps a run `unknown` when a transport failure, interruption, lost lease, or an ambiguous runtime outcome prevents safe confirmation. It never automatically repeats that run. An unknown run blocks subsequent work for that user's computer until a reconciliation feature is implemented. Request IDs deduplicate run creation per Bot; the API requires a valid session and same-origin JSON writes.

The provisioner creates only the deterministically named tenant/user resources and checks their expected ownership and configuration before use. It does not replace existing objects or delete PVCs. Its in-cluster Kubernetes client uses TLS, a bounded set of resource types and create-only requests; cluster permissions, production deployment and actual multi-tenant network isolation remain to be configured and independently tested. The provisioning logic was tested with `kubectl` against a disposable namespace in local K3D, including readiness and a second idempotent read. The Kubernetes HTTP client was tested separately against an isolated TLS server, not against a real cluster service account. Scheduler/API tests used disposable MySQL databases with simulated execution; they do not yet prove an end-to-end public Agent task.

`startPiRuntime` now provides an opt-in wiring path and is disabled by default. It requires private model-key, desktop signing-key and TLS-key files; a matching gateway certificate for the internal service; a Kubernetes API URL, CA and projected token; a pinned desktop image; and model configuration. Projected Kubernetes tokens are reread for each request so rotation does not require restarting the process. No production RBAC, model secret, gateway Service, or enabled environment configuration has been applied. The production control-plane role must be narrowly reviewed and exercised in an isolated namespace before use; the public browser still has no run UI.

The feature branch now includes a conditional run UI. With a simulated identity and executor, its browser test covers queued, running, completion, refresh, account isolation and an ambiguous submission response without retry. The authenticated HTTP API, MySQL queue, scheduler and event history were exercised together with a simulated executor. The real-model K3D tests above and these simulated application tests are separate evidence; an authenticated public run has not been demonstrated.

Before enabling a public Agent, the current design still needs a server-enforced approval boundary for external side effects. The copied Pi adapter includes Bash and browser tools, so instructions in the model prompt alone cannot enforce approval. Cluster permissions also need a design that cannot read or modify other projects' resources; granting broad cluster-wide Secret or workload access to the public control plane is not acceptable. The opt-in runtime must remain disabled until these boundaries and the actual user computer lifecycle are verified.

The runtime now refuses to start when both `NODE_ENV=production` and `COKE_GROK_PI_ENABLED=1`. This prevents the current production image from accidentally exposing the incomplete integration; the guard is to be removed only after the missing boundaries are implemented and tested.

The feature branch also contains an approval persistence layer, authenticated same-origin decision API and conditional chat card. Tests with disposable MySQL verify ownership, denial, expiry, matching the approved action, a valid run lease, and atomic one-time consumption even under concurrent requests. The simulated browser test exercises an approval and recovery from an ambiguous response without automatically repeating it. These records are **not yet connected to the Pi tools**; their existence does not enforce approval by itself. In particular, Bash and browser actions must not be enabled publicly until there is an effective server-enforced boundary.

The internal gateway now also accepts approval requests using a short-lived capability bound to the claimed run and its current lease. Tests verify that a different run's capability cannot inspect or consume the approval, and that approval consumption requires the exact action and succeeds only once. The Pi tools and desktop worker do not yet call this gateway, and the capability channel is not a complete enforcement boundary while the Agent can reach alternative execution paths. Production remains disabled.

An additional isolated K3D test ran the in-cluster Kubernetes client using a projected service-account token and a namespace-scoped Role. It could read its one allowed ConfigMap and received denials for Secrets and another project's namespace. The temporary test namespace was removed. This validates the client and Kubernetes enforcement for that limited read case, not the broader permissions needed to create personal desktop namespaces and workloads.

An isolated K3D NetworkPolicy test confirmed that a test Pod permitted by a policy could connect to a target Pod while an otherwise equivalent denied Pod could not. This verifies enforcement for that single ingress case on the current cluster; it does not establish the eventual Agent egress, noVNC, worker, DNS or cross-namespace policy. The current desktop and Agent containers share a Pod network namespace, so a Pod-level NetworkPolicy cannot isolate them from each other. The production design must close that bypass before approval can be considered enforced.

`canonicalComputerAction` is a proposed server-side action format that binds a specific validated input, the current page location hash and a screenshot hash. Tests check stable canonicalization, changed-page and changed-image fingerprints, invalid coordinates, paths and unrecognized fields. It is not yet connected to the worker or the approval gateway, and a fingerprint alone is not sufficient user-facing context for approving a visual click. The approval UI must show the relevant desktop state and the worker must recheck it immediately before executing.

An in-process `ComputerBroker` demonstrates the intended approval sequence with real MySQL records and a simulated worker: it rejects unapproved, denied, changed-screen, user-controlled and repeated actions. Its worker interface requests a state-and-ownership check at execution time. That test does not exercise the desktop worker, and the broker is not exposed to Pi; the test is not evidence of real enforcement. Approval state consumed before a transport error does not authorize an automatic retry.

An experimental guarded worker now serializes worker-mediated takeover and actions, compares a fresh screenshot and page URL immediately before the action, and requires a distinct control token. The previous worker-token action endpoints are denied in guarded mode. This serializes requests handled by the worker but cannot stop a web page from changing itself between the comparison and browser action; it is not a full atomic transaction with the external site. The worker has not yet been separated from Agent networking, and the Agent can potentially reach Chromium's local debugging endpoint or other channels. This guarded mode is not enabled in production and is not yet a complete approval boundary.

The feature branch now contains an experimental mediated bridge. It checks the run owner and active lease before reading the desktop or creating/consuming an action approval. The snapshot comparison serializes worker-mediated actions but cannot prevent a page from changing independently between comparison and action. Single-screen tasks remain serialized; no multi-screen equivalence is claimed.

The experimental Pi UI now has a personal computer panel with periodic screenshots, a take-control/return control and click, type and Enter actions. The HTTP server selects the desktop solely from the authenticated session; browser writes require the configured same origin, validated commands and user ownership enforced by the worker. It does not provision an idle computer merely by opening the panel; the current task workflow provisions one when needed.

The opt-in runtime now uses a separate desktop provisioning broker over TLS with a private capability, rather than reading Kubernetes credentials in the web control process. The broker accepts only a pair of validated tenant/user IDs, constructs the fixed personal-computer resources itself and does not expose arbitrary Kubernetes operations. The client verifies that the returned Agent endpoint belongs to the requested owner. The broker has a bounded request size and concurrency, and its container can be built using `npm run build:desktop-broker` and `Dockerfile.desktop-broker`. Its test image is not a release image.

An isolated K3D test ran the actual broker, client, provisioner and Kubernetes client using a service account bound to one pre-created personal namespace. It created both desktop Pods and then repeated the idempotent read; attempts to read a Secret or Namespace and create a ConfigMap in the existing project namespace were denied. The test removed its own namespace and RBAC objects. The broker and client communicated over TLS inside the test Pod, so this does not prove the eventual inter-Pod network policy. This service account could not create new namespaces: a safe namespace bootstrap and a reviewed privilege boundary for dynamic users remain unresolved. A compromised broker with broader cluster permissions would still carry that risk; the new API boundary alone does not make those permissions safe. The public runtime remains disabled and no broker or RBAC has been deployed there.

An experimental namespace bootstrap now generates separate service-account roles and Kubernetes `ValidatingAdmissionPolicy` rules. The bootstrap identity may create namespaces and RoleBindings, but admission restricts it to correctly labeled personal-computer namespaces and one binding to the designated broker role and service account. It cannot delete namespaces or read project Secrets. The `NamespaceBootstrap` implementation derives the namespace from the owner, creates or verifies the namespace and binding idempotently, and rejects drift without replacing existing objects. This uses Kubernetes' [validating admission policy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/) and [RBAC bind restrictions](https://kubernetes.io/docs/reference/access-authn-authz/rbac/).

On local K3D 1.35, a test installed policies scoped exclusively to a temporary service-account identity, used Kubernetes impersonation to exercise the actual API, and created two temporary personal namespaces and the designated bindings. It verified repeated bootstrap calls and rejected a different namespace prefix, mismatched owner label, extra annotation, custom finalizer, incorrect subject, `cluster-admin` role and a binding in the existing project namespace; it also verified the test broker could not read Secrets in that existing project. The test removed its own cluster-scoped policies, roles and temporary namespaces. It waited independently for both policies to reject a server-side dry run: their enforcement became visible at different times during testing. Therefore installing policy objects alone is not proof that both are enforcing; a production installer must verify both before making the bootstrap service-account token available and must revoke its permissions before removing policies. Admission policy failure, misconfiguration or removal can otherwise leave the create permissions broad. The bootstrap process still needs its own service, deployment and integration with the provisioning broker; the policies have not been applied to the live project, and the production startup guard remains in place.

The namespace bootstrap and desktop broker are now joined through a separate capability-protected TLS endpoint. The broker asks the bootstrap service to create or verify the owner namespace and binding, checks that the returned namespace matches the owner, and then provisions only namespaced resources. It does not need permission to read or create cluster-level namespaces. The two service entrypoints require distinct private broker and bootstrap capabilities. The bootstrap service has an explicit production startup guard until admission enforcement checks and installation are implemented; building its image does not enable it.

A subsequent isolated K3D integration test used two Pods with different projected service-account identities and a service DNS name protected by TLS. After checking both temporary admission policies were enforcing, the broker Pod called the bootstrap Pod, which created the test user's namespace and RoleBinding; the broker then created the personal computer resources and successfully repeated the request. Its Kubernetes identity was denied a cluster-level namespace read and a Secret read in the existing project both before and after provisioning. The test used test-specific Pod entrypoints, temporary credentials, policies and resources; it did not deploy the production service entrypoints, test the public UI, or prove the final inter-Pod NetworkPolicy. The temporary objects were removed. The production guard and the remaining review of namespace-policy installation, cross-user isolation and external-action bypasses still apply.
